# Localization plan (Nepali, Hindi)

Status: **not started on purpose.** This is audit item X1 (Phase 4 in
[UX_A11Y_AUDIT.md](UX_A11Y_AUDIT.md)). VeriScript's users read Nepali and
Hindi first, so a wrong or awkward interface string costs trust in a product
whose promise is "it will not invent the numbers on your bill". Machine
translations must not ship without a native-speaker review.

## Approach

| | Web studio | Android |
|---|---|---|
| Library | `@solid-primitives/i18n` (typed dictionaries, no runtime parsing) | `flutter_localizations` + `intl`, ARB files, `flutter gen-l10n` |
| Catalogues | `webapp/frontend/src/i18n/{en,ne,hi}.ts`; `en` is the typed source | `mobile/lib/l10n/app_{en,ne,hi}.arb` |
| Locale choice | browser language, overridable in the top bar, remembered like the theme | device locale, overridable in Settings |
| `lang` attribute | `<html lang>` follows the UI; Devanagari tokens keep `lang="ne"`/`"hi"` | `Locale` on `MaterialApp` |
| Numbers | Western digits by default; an option for Devanagari digits in counts (never in OCR output) | same |

## Order of work

1. Extract every user-facing string into the English catalogue. Do this in
   one change per app, so the UI never mixes extracted and literal strings.
   The tests keep finding text by its English value.
2. Add a CI check that fails on string literals in JSX or Text widgets
   outside the catalogues, using a small allowlist for brand names and file
   names.
3. Draft `ne` and `hi`. Mark each entry `reviewed: false`.
4. Native-speaker review: the reviewer checks each screen in context
   (screenshots generated by the Playwright and Flutter tests) and flips
   `reviewed`.
5. Enable a language in the switcher only when all its entries are reviewed.
6. Re-run the accessibility gates in each language. Devanagari wraps and
   measures differently, so check the 200% text-scale layouts again.

## Size

About 220 strings in the web studio and about 300 on Android. That is about
one week of engineering, plus the review time.
